# Supabase game runtime

## Backend cutover

The generated game's app-facing backend now uses Supabase exclusively:

- Email/password Auth through official `@supabase/ssr` / `@supabase/supabase-js`
  clients, HTTP-only same-site cookies, `auth.getUser()` validation, SDK refresh
  and PKCE confirmation-code exchange.
- Verified Auth UUIDs resolve to immutable `vault_player_bindings`. User
  metadata never supplies staff roles, balances, or the welcome amount.
- A consistent published catalog from `vault_runtime_catalog()`. There is no
  Payload or bundled-JSON fallback.
- The existing authoritative TypeScript game/value engine and cryptographic
  server-side rolls, committed through `vault_commit_game()` into the existing
  append-only World snapshot stream, or the private current snapshot and replay
  receipts after the optional manual economy storage cutover.
- Server-computed canonical actor/command hashes and exact receipts. Explicit
  serialization failures reload both economy and catalog; ambiguous failures
  require retrying the **same request key**, never generating a new roll.
- Binding/rules/catalog-revision validation and first-opening marking in one
  SQL transaction. Stock, distinct-player, lifetime, UTC daily and cooldown
  limits share the card-and-currency snapshot commit.
- Existing inventory, grading, displays, jobs, market, trades, auctions, mystery
  rooms, reward packs, chat and leaderboards all use that same stream.

This is the approved **fresh Supabase game**. No old Payload accounts, balances,
cards or history are imported or deleted. Old Payload app/CMS cookies do not
authenticate the game. Platform-managed `/admin` and API scaffold are untouched,
but are not the game's backend or operator authorization. Legacy CMS support
operations cannot modify the new Supabase economy.

## Required database step

After the two original schema migrations and catalog import, apply each missing
additive migration once in Supabase SQL Editor as `postgres`, in this order:

```text
supabase/migrations/20261118000100_vault_runtime_adapter.sql
supabase/migrations/20261119000100_vault_studio.sql
```

The runtime adapter adds the private catalog/commit boundary; the studio adds
audited card/case saves and atomic economy activation. Installing the SQL does
not activate economy 2.2 or compensate players. Do not rerun installed migrations,
reset the economy, or reimport the catalog. Review the upgrade in `/operator`
before entering `CONFIRM` to activate it.

## Server configuration and diagnostics

For external hosting, use the clean project generated by `pnpm run export:external`;
see `docs/external-deployment.md`. It has no Figma/Payload dependency and
requires explicit `SUPABASE_URL` and `SUPABASE_ANON_KEY`, without a built-in
project fallback. The managed workspace can also override its public defaults
with those variables. A changed project URL requires that project's public key,
never an implicit reuse of the old key.

The Next.js application server needs `SUPABASE_SERVICE_ROLE_KEY`, saved through
Make settings → Environment variables (or an external server host's secrets).
It must never be stored in browser code, props, SQL rows, chat, logs or Git.
Supabase Edge Function secrets do not configure the Next.js server.

Inside Make, the project URL/public key default to generated
`utils/supabase/info.tsx`, which is unchanged. If legacy JWT-secret rotation invalidated the public key, set the
current public/anon key under optional server-only `SUPABASE_ANON_KEY`. Never
put a service-role key there. A project URL override must use that project's
matching public key.

`GET /api/backend-status` returns sanitized status only:

- `SERVER_KEY_MISSING`: no server key in the running app.
- `SUPABASE_CONFIG_MISSING`: set/repair the host's Supabase project URL and public key.
- `SERVER_KEY_REJECTED`: the project rejected the saved credential.
- `RUNTIME_SQL_REQUIRED`: install the additive SQL above.
- `STUDIO_SQL_REQUIRED`: install the studio migration above.
- `ECONOMY_ACTIVATION_REQUIRED`: an authorized operator must preview and activate
  economy 2.2; SQL installation alone does not change welcome rewards.
- `SUPABASE_UPSTREAM_ERROR`: an upstream 5xx response; check the connection and
  project availability, then retry.
- `DATABASE_NOT_READY`: another setup/connection failure; no fallback is used.
- `CONNECTED`: the private catalog RPC was reachable. This is not proof of
  successful signup, case publication or every gameplay workflow.

An ordinary agent shell and the running Next.js server may receive different
environment injection. Use this runtime endpoint instead of assuming that a
missing shell variable means the server lacks it.

## Accounts

Enable email/password signup in Supabase Auth with your intended confirmation
policy; the app never auto-confirms or bypasses it. With confirmation enabled,
registration displays instructions and grants no credits until verified login.
Configure your site's URL and redirect allowlist in Supabase Auth to include
the deployed site's `/api/auth/callback`. Open PKCE confirmation links in the
browser that registered. Users can also sign in after confirming their email.

A new verified player receives the configured welcome grant once: **1,250
credits after economy 2.2 activation** (the historical 2.1 rules used 500)
through the game commit, not a second wallet/Auth trigger. Repeated login,
interrupted first joins and request retries do not reset balances or grant
credits twice. Logout clears only the app's Supabase session, not CMS cookies.

## Operators and publication

Use a confirmed staff Auth account (on an empty project, create/invite it through
Supabase Dashboard → Authentication → Users first), explicitly assign its UUID a
role in `vault_operator_roles` using the SQL in `supabase/README.md`, then sign
in to the game and visit **`/operator`**. No first-signup promotion, Figma
identity mapping, public role fields, or default admin password is installed.
Public app registration stays closed until economy 2.2 activation so new
collectors cannot accidentally receive the historical 500-credit grant.

The console supports card design and normal/Limited case editors, protected
previews, assigned-card pools, publication, scheduling, stock/player limits,
custom mint-time base values and guaranteed attributes. Opened releases must be
cloned before economic changes; owned cards retain their original snapshots.
Support tools grant currency or real catalog cards with a reason and typed
confirmation. Supabase validates publication; public visitors cannot write.
If already configured, `VAULT_OPERATOR_PASSWORD` remains an additional check
on operator POSTs, never the source of privilege. Every operation checks the
Supabase role; economy support commands also create immutable game history.

### Economy 2.2 rollout

In **Economy update**, preview the current sequence, eligible collectors and
review flags, then enter `CONFIRM`. Activation switches the rules, adds Alloy
(500) and Aether (2,500) packs, and adds existing-player compensation in one
atomic transaction. No balances are reset or historical cards repriced.

Each verified original welcome grant receives
`max(0, 1250 − original welcome grant) + 250` once. Missing or ambiguous
original grants receive no automatic adjustment and are flagged for review.
New accounts subsequently receive 1,250 once. Daily income becomes 150, sorting
jobs pay 40 with a 30-second cooldown and 40/day limit, and the game offers
durable daily objectives and streak tracking. Retrying activation cannot
duplicate compensation.

Cases pinned to a different configuration remain disabled; review deliberate
version pins before rollout. SQL installation and exporting source do not
perform this activation.

## Verification

```sh
pnpm run typecheck
pnpm run test:unit
pnpm run test:sql
pnpm run test:e2e supabase-cutover.spec.ts
figma make verify-deploy
```

SQL tests use isolated PGlite databases with the actual RPCs and real catalog
import: first join, exact receipts, three-card pulls, first-opening marking,
competing buyers, stale-catalog rejection, forged bindings and browser denial.
Engine tests cover all existing game systems and the new case limits.

Focused browser tests visit every public route and check legacy-cookie
isolation and unauthenticated/operator denial. The older live gameplay browser
suite needs a reachable project and usable confirmed test accounts; its former
fake `@test.vault.invalid` signup assumptions are not a Supabase Auth test
strategy. Do not disable verification or add an auth bypass to pass them.

**Signed-in production delivery is not established** until a real verified
signup/login, opening/reload, trade/sale/auction/income/chat session and operator
publication pass against the connected project. Static build success is not a
substitute.

Auction timers settle durably on authenticated requests, as before, not a new
scheduler. The process-local throttle is defense in depth, not a distributed
limiter. Add a shared limiter before significant multi-instance traffic. The
whole-World stream retains its existing size/concurrency limits.
